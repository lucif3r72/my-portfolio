Montessori Childcare Website & Admin Portal

01 · OVERVIEW

The Problem

DayStar Montessori Childcare is a licensed Montessori daycare and kindergarten in Delta, British Columbia. Its public website had already been designed as a set of static pages, with layouts, palette, typography and logo all settled. What the school lacked was a way to run it: events needed publishing and archiving, photo galleries needed uploading, and parent enquiries needed to land somewhere safe and trackable, without anyone touching code.

The brief had two halves with opposite rules. On the public site the design was fixed: make it dynamic, preserve it exactly, and flag any technical deviation rather than quietly improving it. For the admin portal I designed everything from scratch, but inside the same design system, with security treated as non-negotiable because the site stores parents' contact details.

02 · APPROACH

How We Solved It

Static pages became PHP templates with shared header, footer and call-to-action components, and the Events section was wired to a MySQL database. Everything the school edits sits behind a single-admin portal, and every primary page keeps a clean, readable URL.

The portal reuses the public site's colours, type and buttons, but behaves like real admin software: a collapsible sidebar, a topbar, and re-skinned data tables for events, parent enquiries and an activity log. It is built from reusable components, so future modules such as Tutors or Programs can slot in without a rebuild.

Key Requirements
01

A Design That Couldn't Change

The public pages were already designed. The job was to make them dynamic without altering the look, and to raise any technical deviation rather than quietly “fix” it.

02

Staff, Not Developers

School staff needed to manage events and galleries themselves, including events whose photos arrive days later, or never.

03

Parents' Details, Handled Carefully

The enquiry form stores contact details and IP addresses, so spam protection, privacy and security had to be designed in from day one.

KEY DESIGN DECISIONS
Admin UX

An Admin Built on the Brand

The portal inherits the public site's palette, type and buttons, so it feels like one product, while a collapsible sidebar and re-skinned data tables make it work like proper admin software.

Content Lifecycle

Events With a Manual Lifecycle

Events move between Upcoming, Archived (Awaiting Gallery) and Past by admin choice, never automatically by date, so an event that has finished but isn't photographed yet never shows as a broken page.

Galleries

Galleries That Stay Light and Accessible

Up to 20 images per event, converted to WebP on upload, with required alt text, a chosen cover image, reorderable order and a lightbox that works from the keyboard. An event with no gallery is a normal, valid state.

Trust & Security

An Enquiry Flow Parents Can Trust

Enquiries are saved and emailed to the school behind CSRF protection and rate limits (3 per 15 minutes, 10 per day per IP). If something fails, the form says so plainly instead of pretending it worked.

03 · RESULTS

Outcome

DayStar is live at daystarchildcare.ca. The public site keeps its original design, while events, galleries and parent enquiries are managed through a purpose-built admin portal, backed by hardened security, privacy-conscious analytics that never store a raw IP address, and a deployment guide for the school's shared hosting.

04 · REFLECTION

What I Learned

This project was a lesson in designing inside constraints. With the public design fixed, the craft moved to the places nobody notices until they need them: the empty gallery, the event that has finished but isn't photographed yet, the failed email, the admin who just wants to publish something quickly.

It also reinforced that security and accessibility are design material, not a later pass. Required alt text, keyboard-friendly galleries and honest error states are interface decisions as much as engineering ones.
